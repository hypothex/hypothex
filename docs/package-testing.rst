Installed package acceptance
============================

The ``package`` pytest suite builds the production UI, creates an sdist and a
wheel through ordinary ``uv build``, then installs that wheel with its default
runtime dependencies into a disposable Python 3.13 environment outside the
checkout. Product assertions execute with that interpreter and ``-I``; the
source environment only orchestrates the checks. No development server is used.

Automated verification
----------------------

From the isolated implementation checkout::

   uv sync --locked --all-groups
   bun install --cwd ui --frozen-lockfile
   (cd ui && bunx playwright install chromium)
   (cd ui && bunx tsc -p package-e2e/tsconfig.json)
   HX_PACKAGE_ARTIFACTS="$(mktemp -d /tmp/hx-package-artifacts.XXXXXX)" \
     uv run pytest -m package tests/packaging/test_installed.py -v

The maintainer fixture scripts run by absolute path under archived interpreters,
so their sibling imports need an explicit search path for type checking::

   uv run ty check tests/packaging --extra-search-path tests/packaging

All five tests are required. Missing fixtures, Bun, browsers or packaged files
fail rather than skip. The default pytest selection excludes package and Docker
acceptance; unit tests for the package harness remain in the default suite.
The separate mandatory ``package`` CI job runs these same checks with Chromium.

The checks cover installed imports, default dependency closure, static assets,
Alembic resource/head and metadata parity, fresh token and scoped-team servers,
CLI pairing, real sends to disposable loopback notification sinks, and persisted
paired credentials across restarts. Light and dark browser projects exercise
accessible token unlock or browser pairing and deep-link reloads against the
wheel's static UI. Fresh scenarios add one finished synthetic local sweep
through installed APIs so the legacy sweep URL redirect has populated input;
no host process or training job is launched for that fixture.

The immutable schema-3 input was generated by archived revision
``a4441256f39d014d9ad43dea976af1b448f163e3``; the independent schema-4 input by
``e73b8105df32a1d2488477c48e680cb5de922771``. Each fixture records its source,
actual SQL schema, complete query oracles, and bound evaluation byte hashes.
Ordinary tests restore SQL dumps and allowlisted path fields into new temporary
homes. They never regenerate the oracle with current code. Upgrade, restart and
explicit reindex must preserve records, scores, strict bound comparisons,
notebook/settings data and paired/revoked session semantics. Schema-4 checks also
preserve names, literal search, parent links, metric directions, saved views,
selected-score boards, curves and carried index state.

SQLite upgrades automatically rebuild the disposable index. ``hx db upgrade``
is for PostgreSQL; it is not a SQLite upgrade command. The resource test executes
the packaged Alembic revision against disposable SQLite for metadata parity;
the separate Docker suite owns PostgreSQL integration.

Artifacts and isolation
-----------------------

``HX_PACKAGE_ARTIFACTS`` selects only the retained evidence destination. Builds,
installations, private homes, browser output and server logs live in a separate
owned temporary root. The destination retains the wheel and sdist, their SHA256
hashes, build/import/resource/migration reports, fixture preservation receipts,
per-scenario browser summaries and a process cleanup receipt. ``build.json``
records HEAD separately from ``source_dirty``, full Git status, and source input
hashes; it checks those input bytes remain stable through the build. An
uncommitted candidate is not represented as a clean build of HEAD. CI also retains
JUnit output. Credentials, homes, browser cookies/storage, traces, videos,
screenshots and raw server logs are not published. Publication scans for known
secrets and their URL-encoded forms before copying reports.

Children receive explicit homes, no inherited product routing, no proxy settings
or PostgreSQL environment defaults, and refusal wrappers for real SSH, scheduler,
GPU and Tailscale tools. Product HTTP and browser traffic must stay on loopback.
Dependency and browser installation are provisioning steps. The harness owns
and terminates only its subprocess groups; it does not discover or kill other
servers. These installed children are outside pytest's in-process network guard.

Manual test of the retained wheel
---------------------------------

Use the wheel retained alongside ``build.json`` (which records its exact hash),
and a new temporary home::

   package_demo_root=$(mktemp -d /tmp/hx-wheel-demo.XXXXXX)
   uv venv --python 3.13 "$package_demo_root/venv"
   uv pip install --python "$package_demo_root/venv/bin/python" /absolute/path/to/hypothex-WHEEL.whl
   cd "$package_demo_root"
   env -u PYTHONPATH -u HYPOTHEX_HUB_URL -u HYPOTHEX_HUB_TOKEN \
     "$package_demo_root/venv/bin/hx" --home "$package_demo_root/home" demo --with-team --json
   env -u PYTHONPATH -u HYPOTHEX_HUB_URL -u HYPOTHEX_HUB_TOKEN \
     "$package_demo_root/venv/bin/hx" --home "$package_demo_root/home" serve --host 127.0.0.1 --port 0

Read the displayed loopback URL and selected port. In another terminal use the
absolute installed ``hx`` and same explicit home to run ``whoami --json`` and
``pair --user alice --scope launch --client browser --json``. Open the fresh
pairing URL, fill Device name and select Pair. Verify Home, a task/run, notebook
and Settings. Use an admin browser pairing to inspect Storage. Keep pairing URLs
and credentials private.

For a CLI client create another temporary home, then set ``HYPOTHEX_HUB_URL`` to
the displayed origin and run ``hx --home CLIENT_HOME login PAIR_URL --json``
with a fresh ``--client cli`` pairing offer. ``whoami --json`` should report the
paired user and scope. Stop the server with Ctrl-C and restart it with the same
explicit home and recorded port. The paired login survives; the old local owner
credential is revoked and a new local session is created.

Scoped ``serve --auth`` creates an administrator from normalized ``USER``, with
``owner`` as fallback for an invalid or empty value. Automated team acceptance
pins ``USER=sv`` only in its child environments. Recognized team demo homes use
``sv`` as local owner, even when the caller has a different operating-system
username. Ordinary homes keep the normalized caller identity. The demo's ``sv``
and ``alice`` links are the intended browser logins. All manual checks above
use synthetic demo data in the new temporary home.
